XFCE Window Manager: Silent Failure & Forensic Recovery

This page explains why an XFCE desktop suddenly lost all window decorations, Alt-Tab, and window controls, how we diagnosed the cause, and how we fixed it in a way that survives reboots. No prior knowledge of X11, window managers, or compositors is assumed. Every term is defined the first time it appears, and every command is shown with the exact output to expect in both the broken and healthy states.

The short answer

The window manager — xfwm4, the program that draws title bars, borders, and buttons and handles Alt-Tab — was not running. It failed to start on every login because the X display server was not advertising an optional feature called RENDER that xfwm4 needs when it tries to start its compositor. With no window manager, there were no decorations and no Alt-Tab.

The fix is to tell xfwm4 not to start the compositor. That skips the code path that requires RENDER, so xfwm4 stays running. Because there is now no compositor to blend transparency, GTK applications that draw their own decorations (CSD) show a black border where their shadow would be. Setting GTK_CSD=0 tells them to let the window manager draw plain borders instead.

Glossary

Every technical term used on this page, defined once. Skim now, return later.

Window manager (WM)

The program that draws the title bar, borders, and buttons around every window, and handles window-level keyboard shortcuts such as Alt-Tab. Without a WM running, applications still draw their own content, but no frame surrounds the window: it cannot be moved with the mouse, resized, or minimised from a title bar, and Alt-Tab does nothing.

On XFCE, the window manager is xfwm4, a single process.

X11 / Xorg (the display server)

The program that owns the screen, keyboard, and mouse, and mediates between applications and hardware. Every graphical action goes through it. Xorg is the classic X11 server; Xwayland is a compatibility layer under Wayland. If you see DISPLAY=:0.0 in your environment, you are on X11.

XFCE

A lightweight desktop environment that provides the panel, the Applications menu, settings dialogs, and its default window manager xfwm4.

Compositor

An optional layer that combines every window's pixels into a single final image before the screen shows it. Compositors enable transparency, drop shadows, smooth animations, and the shadows around GTK's client-side decorations.

Without a compositor, every application draws directly to the screen in whatever order it happens to draw, and pixels that were meant to be semi-transparent are instead painted solid.

RENDER / XRender

An X11 extension — an optional feature the display server offers to applications. RENDER provides alpha blending and Porter-Duff composition, which the compositor needs.

If the display server does not advertise RENDER, the compositor cannot function. The X11 extension is named RENDER (all caps). The client library that talks to it is named libXrender (one word). Confusing the two is a common trap: ldconfig -p | grep -i xrender shows the library is installed even when the server does not offer the extension.

xfconf-query

Command-line tool for reading and writing XFCE's per-user settings database. For example, xfconf-query -c xfwm4 -p /general/use_compositing reads whether the window manager's compositor is enabled.

CSD / SSD

Client-Side Decoration — the application draws its own title bar and border. This is what modern GTK applications do, and it relies on the compositor to render rounded corners and drop shadows correctly.

Server-Side Decoration — the window manager draws the title bar and border on the application's behalf. This is the classic X11 model, and it does not need a compositor.

See the diagrams further down for the visual difference.

environment.d

A directory (~/.config/environment.d/) where files named *.conf set environment variables for every program in your graphical session. Read at login by systemd --user.

Each line is a plain NAME=value. There is no export keyword and no shell syntax.

GTK

The graphical toolkit used by most XFCE applications (Thunar, Mousepad, the panel's menus) and by Firefox. Version 3 and later default to CSD, which is why the black border appears when there is no compositor.

What the user observed, and what each symptom meant

SymptomDiagnosis
Every window lost its title bar, border, and close button The window manager is not running. Applications still draw their own content, but nothing is drawing the frame around them.
Alt-Tab does nothing Alt-Tab is not a desktop feature; it is a keyboard shortcut handled by the window manager. No WM, no Alt-Tab.
Firefox minimise/maximise buttons stopped working Firefox asks the window manager to do those actions. With no WM the request has nowhere to go.
A thick black border appeared around the Applications menu This is not caused by the missing WM. It appears once the WM is back but the compositor is off: GTK is drawing a CSD shadow whose transparency is not being blended, so the "transparent" pixels render black. The fix for this is separate from the fix for the missing WM.

Diagnostics you can run

Each command below is read-only. Run it in a terminal. The broken and healthy columns tell you exactly what each line prints in the two states.

Command Broken output Healthy output What it tells you
pgrep -x xfwm4 nothing; exit code 1 a PID, e.g. 139923 Whether the window manager is running.
pgrep -x xfce4-session a PID (session manager is fine) a PID Whether the session manager is alive. If it is and xfwm4 is not, then xfwm4 failed to stay running, not failed to be launched.
xdpyinfo | grep -i render nothing RENDER The root-cause question: does the X server advertise RENDER?
xfconf-query -c xfwm4 -p /general/use_compositing true false Whether the WM is configured to start its compositor (which requires RENDER).

Example of a broken state, run together:

$ pgrep -x xfwm4
$ pgrep -x xfce4-session
4214
$ xdpyinfo | grep -i render
$ xfconf-query -c xfwm4 -p /general/use_compositing
true

Reading this: the WM is not running, the session manager is, RENDER is absent, and the compositor is enabled. That combination is the exact failure. The WM tried to honour use_compositing=true, asked X11 for RENDER, was refused, and exited silently.

The fix, line by line

1. Start the window manager with the compositor disabled

setsid nohup xfwm4 --compositor=off >/tmp/xfwm4.log 2>&1 </dev/null &

Four pieces of this command each guard against a different failure:

  • setsid — run in a new session with no controlling terminal. Without this, the WM dies the moment you close the terminal.
  • nohup — ignore the SIGHUP signal that logout sends. Belt-and-braces with setsid.
  • --compositor=off — do not attempt to enable the compositor. This is the crucial flag: it skips the code path that needs RENDER, so the WM starts and stays running.
  • >/tmp/xfwm4.log 2>&1 </dev/null & — send stdout and stderr to a log, detach stdin, and run in the background so your shell prompt returns immediately.

After this line, pgrep -x xfwm4 prints a PID, and all window decorations and Alt-Tab work immediately.

2. Make the setting survive logout

xfconf-query -c xfwm4 -p /general/use_compositing -s false

This writes false to XFCE's per-user settings database. The next time the session manager starts xfwm4 at login, it reads this value and skips the compositor without any manual command. This is what makes the fix survive reboots.

Verify with:

$ xfconf-query -c xfwm4 -p /general/use_compositing
false

3. Disable GTK client-side decorations (fixes the black border)

export GTK_CSD=0

This line, on its own, does nothing to fix the missing WM. It removes the black border that otherwise appears once the WM is back without a compositor. The next section explains why.

4. Persist GTK_CSD across sessions

mkdir -p ~/.config/environment.d
printf 'GTK_CSD=0\n' > ~/.config/environment.d/10-gtk-csd.conf

environment.d files are plain NAME=value, one per line. No export, no quotes, no shell syntax. Read at login by systemd --user, which passes them to every graphical program: 

$ cat ~/.config/environment.d/10-gtk-csd.conf
GTK_CSD=0

Adding the same line to ~/.bashrc is a second safeguard for programs you launch from a terminal.

Why disabling the compositor removes the black border

The black border is not caused by the fix; it is caused by the absence of a compositor that the fix leaves in place. Here is the mechanism, with diagrams.

With CSD (client-side decoration, the modern GTK default)

┌──────────────────────────┐  <- app draws this border
│  ●  ●  ●     Firefox     │  <- app draws these buttons
├──────────────────────────┤
│                          │
│      app content         │
│                          │
└──────────────────────────┘  <- app draws this border

The application draws its own title bar and border, and adds a soft drop shadow around the edges for a modern look. The shadow is semi-transparent black. To render it correctly, the app relies on the compositor to blend those semi-transparent pixels with whatever is underneath.

Without a compositor

No compositor means nothing blends the transparency. X11 paints every pixel directly to the screen. The "semi-transparent black" shadow region becomes solid black. On a menu, this appears as a thick black border.

With GTK_CSD=0

┌──────────────────────────┐  <- WM draws this
│         Firefox          │  <- WM draws this
├──────────────────────────┤
│                          │
│      app content         │
│                          │
└──────────────────────────┘  <- WM draws this

The application stops drawing its own border. The window manager draws a plain title bar using the WM theme. No transparency, no shadow, no black pixels. This is the classic SSD model.

That is why the fix is two-part: disable the compositor (so xfwm4 can start at all), and disable CSD (so menus and CSD windows still look correct without a compositor).

Outstanding item: RENDER is still absent on the X server. That is the deeper issue, and the fix sidesteps it rather than solving it. Restoring RENDER on the X server is a separate project involving Xorg configuration and the graphics driver; until that is done, the compositor must stay off.

Forensic monitoring

The failure was invisible because xfwm4 exited before its logging subsystem opened. Nothing was written to journalctl, ~/.xsession-errors, or XFWM4_LOG_FILE. A future regression would be equally silent. These tools close that gap.

statedrift — tamper-evident snapshots

statedrift records the state of the whole host (packages, services, users, network, files) as SHA-256 hash-chained snapshots. Each snapshot commits to its predecessor, so a retroactive edit to an old snapshot is detectable. 

sudo statedrift init
sudo statedrift snap
statedrift diff HEAD~1 HEAD

statedrift verify reports whether the chain is intact. statedrift export produces a redacted evidence bundle for an external auditor or a support ticket.

configsnap — Fedora-native baseline

configsnap is packaged in Fedora's own repositories. It records "important system state" — packages, services, kernel modules, user accounts, network interfaces — and, when the phase name contains post or rollback, automatically diffs against the stored pre snapshot[reference:5]. 

sudo dnf install -y configsnap
sudo configsnap -t mychange -p pre  -d /var/log/configsnap -v
# ... change something ...
sudo configsnap -t mychange -p post -d /var/log/configsnap -v
# re-diff without recollecting:
sudo configsnap -C --pre=pre -p post -t mychange -d /var/log/configsnap -v

The one-shot wrapper in this repo collapses that into three subcommands: 

sudo scripts/configsnap-baseline.sh pre
sudo scripts/configsnap-baseline.sh post
sudo scripts/configsnap-baseline.sh report <tag>

It writes under /var/log/configsnap/<tag>/, passes -v so progress is visible, and refuses to run without root because configsnap collects data as root.

tibet-snap — cryptographic snapshots and rollback plans

tibet-snap creates TIBET-sealed snapshots (paths, SHA-256 hashes, timestamps, sizes, permissions) and chains every operation into a tamper-evident audit trail. Its distinguishing feature is rollback plan generation: given a snapshot, it produces a concrete list of restore/remove/revert actions[reference:7]. 

python3 -m pip install --user tibet-snap
tibet-snap create baseline /etc/X11 /etc/systemd /etc/xdg
tibet-snap list
tibet-snap verify <id>
tibet-snap compare <id_a> <id_b>

Rollback plans are exposed through the Python API, not the CLI: 

python3 - <<'PY'
from tibet_snap import SnapEngine
engine = SnapEngine(store_dir=".tibet-snap")
snap = engine.create_snapshot("pre-deploy", paths=["/etc/X11"])
for action in engine.rollback_plan(snap.id):
    print(action["action"], action["path"])
PY

The one-shot wrapper in this repo does create → list → verify → rollback plan in a single invocation: 

scripts/tibet-snap-baseline.sh baseline-$(date +%Y%m%d-%H%M%S)

It probes for tibet-snap and falls back to tibet-wayback, since upstream marks tibet-snap deprecated in favour of that successor[reference:8]. The store lives at ~/.local/state/tibet-snap by default; override with TIBET_STORE=….

If this happens again

  1. No decorations, Alt-Tab dead. Run pgrep -x xfwm4. If it prints nothing, the WM is not running.
  2. Start it manually, compositor off. 
    setsid nohup xfwm4 --compositor=off >/tmp/xfwm4.log 2>&1 </dev/null &
    If decorations return, the persistent setting was overwritten — reapply it with xfconf-query -c xfwm4 -p /general/use_compositing -s false.
  3. WM still dies immediately. Read /tmp/xfwm4.log. If it is empty, the failure happened before logging started, which is the RENDER case. Confirm with xdpyinfo | grep -i render.
  4. RENDER is present but the WM still dies. Check /var/log/Xorg.0.log for driver errors, and try a different compositor backend if you need compositing.
  5. Decorations return but menus are black. The compositor is off and CSD is on. Add GTK_CSD=0 to ~/.config/environment.d/ and log in again.
  6. Need evidence for a support ticket. Run bash scripts/forensic-baseline.sh; it produces a single .tar.gz with diagnostics, configsnap output, and a sealed tibet snapshot listing.
